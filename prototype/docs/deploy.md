# Putting the app online (free tiers: Render + Neon + cron-job.org)

This sets up the live app in **test mode**: real data, but no WhatsApp messages are sent. Connecting
WhatsApp and the step-by-step switch to real sending are in [go-live.md](go-live.md).

| Service | Free tier | Job |
|---|---|---|
| Neon | Postgres database | Keeps all the data. Render's free disk is wiped on every restart, so the data can't live there. |
| Render | Web service, sleeps after 15 min without visits | Runs the app |
| cron-job.org | Free scheduled calls | Calls `POST /jobs/tick` every 10 minutes. This wakes the app and sends what is due. |
| GitHub Actions | Free minutes | A daily encrypted copy of the database |

## 1. Database (Neon)

1. Sign up at neon.tech and create a project. Pick the region closest to India (Singapore).
2. Press **Connect** and copy the connection string, e.g.
   `postgresql://user:password@ep-xxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`.
3. Optional: put it in `prototype/.env` as `DATABASE_URL=...` and check it from your computer:
   ```bash
   python -m app.check
   ```
   The check only reads. It should say `Connected` and `The database is empty`; the tables are created
   when the app first starts.

   With the live string in `.env`, the app on your computer works on the live data. Its automatic
   sending is off by default in that case (`LOCAL_SCHEDULER`), so it never sends alongside the server. The
   tests never touch this database.

## 2. App (Render)

1. The code must be on GitHub (it is: `whatsapp-dashboard`, or `main` once merged).
2. In Render: **New → Blueprint**, pick the repository and branch, and set the Blueprint path to
   `prototype/render.yaml`.
3. Render asks for the values marked `sync: false` in `render.yaml`:

   | Name | Value |
   |---|---|
   | `DATABASE_URL` | The Neon connection string |
   | `ADMIN_USERNAME` | The owner's login name |
   | `ADMIN_PASSWORD` | A strong password, 10+ characters |
   | `BUSINESS_NAME` | e.g. `ABC Frozen Foods` |
   | `BUSINESS_UPI_ID` | e.g. `abcfrozen@okaxis` |
   | `WHATSAPP_PROVIDER` | `dryrun` (test mode) for now |

   `SESSION_SECRET` and `TICK_TOKEN` are generated by Render. Leave all `META_...` values out until
   WhatsApp is connected. The full list with explanations is in `prototype/.env.example`.
4. Deploy. On the first start the app creates the tables and the default reminder schedule.
   - With `APP_ENV=production` it **refuses to start** if a secret is weak or missing, and the log names it.
5. Open `https://<service>.onrender.com/healthz`. It should show `{"ok": true}`. Then log in.
6. To run the same check on the server: Render → the service → **Shell** → `python -m app.check`.
   (The Shell tab may need a paid plan; the deploy log shows the same problems if it refuses to start.)

## 3. The wake-up call (cron-job.org)

1. Copy `TICK_TOKEN` from Render (service → Environment).
2. On cron-job.org, create a job:
   - **URL:** `https://<service>.onrender.com/jobs/tick`
   - **Schedule:** every 10 minutes. To use less of the free database, limit it to the sending hours, e.g.
     every 10 minutes from 08:00 to 21:00 India time. Set the job's time zone to Asia/Kolkata. If the owner
     changes the sending hours on Settings, change these hours too.
   - **Advanced:** request method **POST**, header `X-Tick-Token` = the token, timeout 30 s or more.
3. Check the job's history. Answers look like:
   - `{"reminders":"waiting until 10:00"}` (before the daily send time)
   - `{"reminders":"ran","sent":3,...}`
   - `{"reminders":"paused"}` (Pause all sending is on)
   - `{"reminders":"another tick is running"}` (a slow tick overlapped; harmless)

   A sleeping free service takes 30–60 s to wake, so the first call after a quiet spell may time out. The
   next one works.

A tick is safe to run any number of times: nothing is ever sent twice.

## 4. Daily backup (GitHub Actions)

The workflow `.github/workflows/backup.yml` makes an encrypted copy of the database every night at
03:00 India time and keeps each one for 30 days.

1. GitHub → the repository → Settings → Secrets and variables → Actions → **New repository secret**:
   - `BACKUP_DATABASE_URL`: the Neon connection string.
   - `BACKUP_PASSPHRASE`: a long passphrase. **Write it down somewhere safe.** Without it the backups can't
     be opened.
2. GitHub only runs scheduled workflows from the default branch, so this starts once the code is merged
   into `main`. To test it straight away: Actions → *database backup* → **Run workflow**.
3. Each run has a `db-backup-YYYY-MM-DD` file under **Artifacts**.

GitHub pauses scheduled workflows in a repository with no activity for 60 days. It emails a warning
first; one click re-enables it.

**Restoring** (to a new, empty Neon database), on a computer with Postgres tools and gpg:
```bash
gpg --decrypt db-backup-2026-11-20/backup.dump.gpg > backup.dump
pg_restore --no-owner --no-privileges --dbname="postgresql://...new database..." backup.dump
```
Then point `DATABASE_URL` on Render (and `BACKUP_DATABASE_URL`) at the new database.

Neon also keeps its own short history, so you can restore to a point in the last day or so from its
dashboard (Branches → Restore).

## 5. Check it works (test mode)

Go through the smoke checklist in [go-live.md](go-live.md#smoke-checklist). In test mode, every message
appears on the Messages page as "Test mode" instead of being sent.

## Run the tests against Postgres yourself

```bash
cd prototype
TEST_DATABASE_URL=postgresql+psycopg://user:pass@localhost:5432/reminders_test python -m pytest -q
```
Use an **empty, throw-away** database, **never the live one**: the tests drop and recreate every table. CI
does this on every push (`.github/workflows/ci.yml`).
